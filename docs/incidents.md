# Incidents

## 2026-11-23 22:16 — 定时发送失败(open failed)

**现象**:当天 22:16 的计划时刻没有发出,`send-log.jsonl` 记录
`{"event":"send-failed","reason":"open failed","pick":{"bucket":"日番",...}}`。

**根因**(两层,叠加放大):

1. `pick.js --open` 在 `goto` 之后只等 2.8 秒就去找卡片。抖音搜索结果页是前端渲染,
   实测结果要 15–40 秒才出现,于是「页面上没有卡片」→ card not found。
2. 修复过程中我加了错误码检测 `/50[023]|Bad Gateway/`,结果 **页脚的 `京ICP备11010802050006号`
   命中了 `500`**,于是每次都在第一轮轮询时就 `break`,连 40 秒都没等满。

**影响**:22:16 这条丢失。22:52 那条在修复后正常。

**修复**:
- 打开卡片改为轮询(1.5s × 26 次 ≈ 40s),不再用固定等待;
- 错误检测只匹配 `Bad Gateway|kngx|访问过多|系统繁忙`,不再做裸数字匹配;
- 失败后每个时刻最多重试 2 次(间隔 90s),再失败跳过并记录,避免高频重试。

**教训**:
- 任何「页面里出现 X 就判定失败」的规则,都要先确认 X 不会出现在正常页面的页脚里;
- 改线上正在运行的脚本时,要么先停调度,要么改完立刻做一次单步验证——本次改 `pick.js`
  时线上调度正在重试,导致一次 `Command failed`(子进程读到半写入的文件)。

## 2026-11-24 09:44 — 人机验证导致当日计划全部卡住

**现象**:切换到新程序后的第一个早晨,`09:44`、`09:51` 两个时刻连续 `no candidate`;
浏览器打开后 `document.body.innerText` 只有 1 个字符,搜索页空白。

**根因**:抖音弹出行为验证(「点击两个形状相同的物体」),页面标题变成「验证码中间页」。
不是程序逻辑问题——同一时刻用同一 profile 手动打开也是验证页。

**诱因**:前一天为了做端到端验证,反复在搜索页之间导航了几十次,远超正常使用强度,
触发了平台侧风控。

**处理**:
- 账号在数据库里置为 `enabled = 0`,停止所有尝试;
- 保留浏览器窗口给人工完成验证;
- 新增 `captcha` 检测:`/state` 返回 `challenge: true` 时,`sendOne` 直接返回错误并记录
  `captcha-blocked`,该时刻不标记失败、不重试,等人工处理。

**教训**:自动化强度要留余量。测试和生产共用同一个账号时,测试产生的请求量会直接
消耗账号的风控额度。
