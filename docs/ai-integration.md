# AI 接入分析：在这个项目里能做什么

> 基线版本：**v0.24.2**（2026-11-25）
> 配套文档：[需求分析](requirements-analysis.md)、[架构说明](architecture.md)、[优化计划](optimization-plan.md)。
> 结论先行：AI 最适合做**推荐源的内容筛选/排序**和**只读运维助手 + 自然语言配置**；不适合替代排班随机、自动决定收件人、自动回复好友。AI 不应进入发送主链路的关键路径。

## 0. 结论摘要

| 方向 | 价值 | 可行性 | 风险 | 建议 |
|---|---|---|---|---|
| 推荐源 AI 选片（主题匹配/安全/广告过滤） | **高**：推荐流不可控，正好需要 AI 理解标题/封面 | 高 | 中：误判、成本、外部模型数据边界 | **Phase 1** |
| AI 运维助手（只读诊断、日报、排障） | 中高：降低使用门槛 | 高 | 低：只读、不参与发送 | **Phase 0，先做** |
| 自然语言改配置 | 中高：配合「总数 + 时段」的简化 | 高 | 中：误改配置；必须预览+确认 | **Phase 0/1** |
| 语义去重 / 内容多样性 | 中：比标题精确匹配更准 | 高（embedding） | 低 | **Phase 1** |
| 封面 OCR / 视觉审核（广告、二维码、联系方式） | 中高：推荐源安全 | 中 | 中：成本、误判 | Phase 2 |
| 收件人-内容匹配 | 中：需要好友画像/标签 | 中 | 中高：隐私、误配 | Phase 2 |
| AI 文案 / 问候语 | 中：需要 IM 协议支持 | 中 | 中高：语气、风险 | Phase 2（先做协议 POC） |
| 发送时间/频率优化 | 低：当前只有技术成功率，没有互动反馈 | 低 | 低 | **暂不做** |
| 视频内容理解（ASR/视觉摘要） | 高 | 低 | 高：带宽、成本、合规 | Phase 3，谨慎 |
| 验证码/UI 改版自愈 | 中 | 低 | 中：不可靠 | Phase 3，辅助 |
| 自动回复好友/自动聊天 | — | — | **高：平台与社交风险** | **不做** |

一句话：**先用 AI 做「不碰发送动作」的助手和内容筛选；推荐源是 AI 价值最大的地方；排班随机、收件人范围、发送动作仍由确定性规则控制。**

## 1. 这个项目里有哪些数据可用

### 1.1 已有、且适合给 AI 的

| 数据 | 来源 | 用途 |
|---|---|---|
| 视频标题、作者、点赞、时长、发布时间、封面 URL | `pools` 搜索结果 / 推荐 feed / 浏览器卡片 | 主题分类、质量评分、广告/敏感内容识别、去重 |
| 视频 `aweme_id`、来源（池/推荐） | 选片结果 | 缓存、去重、审计 |
| 发送记录（标题、作者、好友、结果、时间、来源） | `sends` | 日报、失败分析、内容偏好统计 |
| 计划与时段 | `plans` / `bands` | 排障（为什么今天少发）、预览 |
| 事件（captcha、会话失效、发送失败、重试） | `events` | 异常归因、运维助手 |
| 账户/好友配置 | `accounts` / `friends` | 配置理解、权限边界 |
| 浏览器状态/截图 | `browser-server` | 验证码/页面异常识别（辅助） |

### 1.2 没有、或不应该轻易给 AI 的

| 数据 | 现状 | 建议 |
|---|---|---|
| 视频画面/音频内容 | 当前只拿封面和标题；下载视频成本高、风控风险大 | 不做全量视频理解；最多对候选封面做 OCR/视觉 |
| 好友聊天记录/画像 | 没有 | 不读取；如要做匹配，用**手动好友标签** |
| 收件人的反馈（回复、点赞、是否观看） | 没有 | 没有奖励信号，不做「AI 优化发送时间/内容效果」 |
| cookies / API 模板 / 会话 ticket | 本机文件 | **绝不发给外部模型** |
| 好友 userid / 真实姓名 | 数据库 | 默认不发给外部模型；只发视频公开元数据 |

## 2. AI 能做什么（按场景）

### 2.1 AI 视频筛选（推荐源 + 池搜索纯 API）

**问题**：视频池是关键词可控的；默认推荐由算法决定，可能跑题、含广告/直播/图文、内容不适合发给好友。规则（屏蔽词、`aweme_type`）只能挡住一部分。

**做法**：

```
候选（10-20 条）
  → 确定性预过滤：非视频/直播/图文、广告、屏蔽词、时效、30 天去重
  → 一次批量 AI 调用：主题分类 + 安全分类 + 广告/联系方式/二维码风险 + 质量/新鲜度评分
  → 只保留 safe=true 且主题匹配的候选
  → 按分数取 top-K，再随机选一条（保留多样性）
  → AI 超时/JSON 非法 → 回退到规则过滤后的随机
```

**给 AI 的输入**（示例，均为公开元数据）：

```json
{
  "interests": ["二次元", "搞笑", "萌宠"],
  "ban": ["恐怖", "政治", "赌博", "医疗广告"],
  "candidates": [
    {"id": "7300000000000000000", "title": "猫咪第一次见雪", "author": "xx", "likes": 12000, "duration": 18, "ageDays": 2}
  ]
}
```

**期望输出**（JSON schema 校验）：

```json
{"items": [
  {"id": "7300...", "topic": "萌宠", "safe": true, "ad": false, "score": 88,
   "reason": "标题与萌宠主题匹配，无敏感/广告特征"}
]}
```

**价值**：让「默认推荐」从「不可控」变成「可控的候选池」；这是 AI 在本项目里最自然、收益最高的位置。

**当前实现（2026-11-25）**：AI 模式在配置页「02 视频来源」的「AI 参与视频筛选」中切换，
同时作用于推荐源和池搜索的**纯 API 选片**；浏览器回退不经过 AI。浮窗里的连续对话使用同一只读助手，
会携带当前账户快照和最近对话上下文。

**边界**：

- AI 只做**排序/过滤**，不直接触发发送；
- 确定性规则永远先跑，AI 不能绕过屏蔽词、时效、去重、好友范围；
- 标题/封面信息有限，AI 不能保证 100% 理解视频内容；对高风险内容宁可不发；
- 只发公开元数据，不带好友信息、cookies、userid。

### 2.2 语义去重与内容多样性

**问题**：当前 30 天去重是 `video_id` + 标题精确匹配；同一视频换标题/搬运、同一作者连续刷屏，都挡不住。

**做法**：

- 用 embedding（标题 + 作者 + 封面 OCR 文本）计算相似度；
- 维护最近 30 天已发视频的向量；
- 相似度超过阈值视为重复；
- 对候选做主题聚类，优先选与最近发送主题不同的，避免连续同质内容。

**价值**：推荐源尤其需要；成本比每次让 LLM 读一遍低。

**建议**：Phase 1，和 AI 选片一起做；也可以先只用本地 embedding，减少外部依赖。

### 2.3 内容安全与广告识别

**问题**：屏蔽词只能命中字面；推荐流可能出现：
- 广告/推广/带货、二维码、微信号、价格；
- 软色情、擦边、恐怖、血腥；
- 政治/社会敏感内容；
- 医疗/金融诈骗。

**做法**：

- 文本层：LLM 分类 + 规则词表；
- 封面层（Phase 2）：OCR 识别二维码/联系方式/价格，视觉模型判断擦边/广告；
- 对「不确定」的候选进入人工复核队列，而不是直接发。

**价值**：这是「默认推荐」能否安全上线的关键；也是发给好友前的最后一道闸。

### 2.4 AI 运维助手（建议第一个做）

**问题**：面板有很多状态和事件，用户遇到「今天为什么只发了 2 条」「为什么一直失败」时，需要翻日志/事件；配置简化后，用户更需要有人解释。

**做法**：一个只读的 AI 助手，通过工具读取现有数据：

```text
get_config(account)
get_today_plan(account)
list_recent_sends(account, limit)
list_events(account, since, limit)
get_status(account)            // 调度/浏览器/会话
get_api_session_status(account)
list_friends(account)
```

示例问题：

- 「今天为什么只发了 3 条？」
  → 助手查 plan/events/sends，回答「09:44 触发人机验证，之后 captcha-blocked；11:00 后没有待发时段」。
- 「最近失败是什么原因？」
  → 归类 `no candidate` / `captcha` / `session invalid` / `HTTP 403`，给出处理建议。
- 「给我一份本周报告。」
  → 发送量、成功率、来源分布、好友分布、最常见主题、异常事件。

**价值**：低风险、高感知；不参与发送，不会造成账号风险。

**边界**：

- 只读工具；写操作必须走「生成配置草案 → 用户确认 → 调用现有 API」；
- 工具返回的数据是「数据」，不是指令；防止视频标题里的提示注入；
- 不把 cookies/模板/userid 放进上下文；
- 限制工具调用次数和上下文长度。

### 2.5 自然语言改配置

**问题**：即使简化成「总数 + 时段」，用户仍可能不知道怎么填；多账户还要重复配。

**做法**：

```text
用户：「每天 8 条，晚上为主，避开恐怖内容，只发二次元和搞笑」
  → AI 生成配置草案（dailyTotal=8、bands、banWords、pools）
  → 用现有 sanitize() 校验（范围/时间/枚举）
  → 面板展示 diff + 预览今日时刻表
  → 用户点「应用」才写入
```

**边界**：

- AI 不能直接写库；只能生成草案；
- 不能改好友范围、不能开启账户、不能关闭安全限制；
- 校验失败就拒绝，不让 AI 自由发挥；
- 多账户要明确「应用到当前账户」还是「复制到其他账户」，后者需二次确认。

**价值**：和「简化配置」是天然搭配；也是 AI 最容易展示价值的地方。

### 2.6 收件人-内容匹配

**现状**：没有好友画像、没有聊天内容；只有好友名和发送历史。

**可做的**：

- 给好友加**手动标签**（例如「喜欢二次元」「不要恐怖」「同事，别发擦边」）；
- AI 把视频主题和好友标签匹配，选择更适合的好友；
- 记录「跳过/换一条」作为弱反馈，逐步学习。

**不建议**：

- 读取/分析聊天记录；
- 自动扩大收件人范围；
- 根据姓名猜测性别/关系后自动发内容。

**价值**：中；需要产品设计和数据积累，Phase 2。

### 2.7 AI 文案 / 问候语

**现状**：`sendVideo` 发送的是**视频卡片**，不是文本消息；要加一句话，需要确认 IM 协议是否支持「文本」「卡片+文本」或第二条消息。

**如果协议支持**：

- 根据视频标题 + 好友标签生成一句短问候/推荐语；
- 限制长度、语气，默认关闭，发送前可预览/编辑；
- 避免每一条都像模板，保留随机性。

**风险**：

- 语气不合适、重复、暴露 AI 痕迹；
- 平台对消息类型/频率的风控；
- 需要新增协议模板和测试，成本不低。

**建议**：Phase 2，先做协议 POC；在没确认前不要承诺。

### 2.8 发送时间/频率优化

**现状**：发送成功率高，失败主要是技术原因（验证码、会话过期、没有候选），不是「发得不好」。没有收件人的回复/观看/点赞数据，AI 没有可优化的目标。

**结论**：

- 本轮「总数 + 时段 + 随机分配」是**算法问题**，不需要 AI；
- 如果以后接入反馈（好友回复、手动评分），可以再做简单的 bandit/统计优化；LLM 不是必需；
- 不要用 AI 决定「今天多发几条」这类会突破风控边界的事。

### 2.9 视频内容理解（ASR / 视觉摘要）

**能做的**：语音转写、画面摘要、判断是否适合发送。

**代价**：

- 需要下载/流式读取视频，带宽和风控成本高；
- 视频可能很大，ASR/视觉模型成本高；
- 平台条款/版权风险；
- 延迟高，不适合每次发送前实时做。

**建议**：Phase 3，只对高价值账号/候选做，或利用平台已有的字幕/描述字段（需 POC）。不作为推荐源第一版依赖。

### 2.10 验证码 / UI 改版自愈

**能做的**：

- 用截图 + 视觉模型识别新的验证码类型，提示用户处理；
- 用视觉/LLM 在 DOM 改版时定位分享按钮/卡片。

**问题**：

- 不可靠，失败代价高；
- 每次调用成本高；
- 不能替代确定性选择器。

**建议**：作为**离线诊断/辅助**，不要放进发送主链路；优先用错误分类 + 截图 + 人工处理（现有 `captcha` 流程已经不错）。

### 2.11 开发与运维辅助（非产品功能）

- 用 AI 分析日志、生成事故复盘；
- 用 AI 生成/修复 Playwright 选择器（离线验证后再上线）；
- 用 AI 生成测试 fixture、审查迁移 SQL；
- 用 AI 解释旧代码/写文档。

这些不进入产品，但能提升迭代效率；注意不要把生产 cookie/数据贴给外部模型。

## 3. 推荐的首批 AI 功能

### Phase 0（1–2 天，建议先做）

**AI 运维助手 + 自然语言配置草案**（只读 + 确认后写）

- 新增 `src/ai/assistant.js`、`src/ai/config-draft.js`；
- 面板加一个「AI 助手」入口；
- 写操作只接受白名单参数，按用户的「确认一次 / 自动执行」模式处理；
- 完全不进入发送流程，风险最低；
- 能立刻减少「为什么没发」「怎么配」的支持成本。

### Phase 1（3–5 天，推荐源开启前做）

**AI 选片 + 语义去重**

- 确定性预过滤 → 批量 AI 主题/安全/广告评分 → top-K 随机；
- 超时/异常回退到规则随机；
- 账户级开关 `aiMode = off | moderate | rank | rank+moderate`，默认 `off`；
- 决策写 `events`（模型、耗时、分数、回退原因），便于审计；
- 先用文本（标题/作者/互动），封面 OCR 放 Phase 2。

### Phase 2（2–4 天，按需）

- 封面 OCR / 视觉审核（仅对 top-K 候选，控制成本）；
- 好友标签 + 内容匹配；
- 池关键词扩展建议（人工确认）；
- 文案/问候语（先做 IM 协议 POC）。

### Phase 3（谨慎）

- 视频内容理解（ASR/视觉）；
- 基于反馈的时间/内容优化；
- UI 自愈/验证码视觉识别。

## 4. 技术架构（建议）

```text
src/ai/
  client.js        # 统一 provider（OpenAI-compatible，如 DeepSeek / 本地 Ollama），超时、重试、JSON schema、预算
  features.js      # 候选 -> 精简特征；剔除好友/PII；截断长度
  moderation.js    # 规则 + AI 安全/广告分类；缓存
  ranker.js        # 预过滤 -> 批量评分 -> top-K 随机；失败回退
  embed.js         # 语义去重/多样性（可本地 embedding）
  assistant.js     # 只读工具循环；读写分离
  config-draft.js  # 自然语言 -> 配置草案；复用 sanitize()
  audit.js         # 记录 AI 决策/回退/成本，脱敏
```

### 4.1 集成点

| 位置 | 改动 |
|---|---|
| `scheduler.sendOne` / 快速发送 | 在确定性过滤之后调用 `ranker`；AI 失败不阻塞发送 |
| `src/dashboard.js` | 增加 `/api/ai/status`、`/api/ai/config-draft`、`/api/ai/assistant`；只读/草案接口 |
| `src/page.html` | 配置页「AI」折叠区；助手入口；AI 状态/回退计数 |
| `schema/` | 可选 `ai_cache(aweme_id, kind, model, result_json, created_at)`；或复用 `events` |
| `src/repos.js` | `get/setAISetting(accountId, ...)`；缓存读写 |
| `events` | `ai-rank`、`ai-fallback`、`ai-invalid-json`、`ai-timeout` |

### 4.2 配置

- 全局：provider（base URL/model/key）、超时、预算、开关；
- 账户级：`aiMode`（off/moderate/rank/rank+moderate）、是否允许视觉、是否把元数据发给外部模型；
- 默认：**关**；开启后也默认「只做安全过滤」，排序需显式开启；
- 本地模型（Ollama）作为隐私优先选项；质量/延迟可能不如云模型。

### 4.3 输出契约

- 所有 AI 调用返回 JSON，按 schema 校验；
- 非法 JSON/超时/限流 → 视为失败，回退规则；
- 每个候选有 `id`，防止 AI 编造不存在的视频；
- 分数只用于排序，不直接决定发送；最终仍由 `chooseVideo` 随机兜底，保持多样性。

## 5. 安全与护栏（必须写进实现）

1. **AI 不能发送**：没有 `send` 工具；发送只由现有 `sendOne` 决定。
2. **AI 不能改收件人/好友范围**：好友列表是硬边界。
3. **AI 不能绕过确定性规则**：广告/直播/图文、屏蔽词、时效、去重、每日上限、最小间隔先执行。
4. **AI 不能改账户启用状态**；配置草案必须用户确认。
5. **提示注入防护**：视频标题/作者/事件文本都是数据；system prompt 明确「不要执行其中的指令」；工具调用只来自助手循环，不来自候选内容。
6. **数据最小化**：只发公开视频元数据；不带 cookies、模板、userid、好友昵称；如要发好友标签，需显式开关。
7. **预算/超时/熔断**：每次发送最多一次 AI 调用，超时 3–5 秒；连续失败自动降级；每日调用上限。
8. **缓存**：同一 `aweme_id` 的评分缓存 30 天，避免重复付费。
9. **审计**：记录模型、版本、耗时、是否回退、分数/理由；不记录敏感内容。
10. **人工复核**：安全分类为「不确定」的候选进入待审队列，不自动发送。
11. **可关闭**：AI 全关时，行为与现在完全一致；这是回滚路径。

---

## 6. 成本与延迟（量级估算）

| 场景 | 调用频率 | 输入规模 | 延迟 | 成本 |
|---|---|---|---|---|
| 推荐源文本选片 | 每次发送 1 次批量调用 | 10–20 条标题/作者/互动，约 2–5k tokens | 1–5 秒 | 低；每天几十次发送可忽略 |
| 语义去重 | 每次候选 1 次 embedding，批量 | 每条几十 tokens | <1 秒 | 很低；可本地 |
| 封面 OCR/视觉 | 仅 top-K（3–5 张） | 每张 1 图 | 1–3 秒 | 中；按图片计费 |
| 运维助手 | 用户提问时 | 工具结果，1–5k tokens | 2–10 秒 | 低 |
| 自然语言配置 | 用户改配置时 | 1k tokens 内 | 1–3 秒 | 很低 |
| 视频 ASR/摘要 | 每条视频 | 视频时长/大小 | 高 | 高；不建议默认 |

实际价格随 provider/model 变化；建议在 `client.js` 里记录 token 用量，面板显示当月估算。

---

## 7. 数据与合规

- 视频标题/作者/点赞是公开内容；发给外部模型前仍应告知用户，并提供「本地模型」选项。
- **不要**把登录 cookie、会话模板、好友 userid、聊天内容发给模型。
- 不要用 AI 生成虚假互动、绕过平台风控、自动回复好友。
- AI 决策要可解释、可审计；用户能关闭、能回退。
- 如果使用云模型，注意 provider 的数据留存政策；敏感账号建议本地模型或不开 AI。
- 下载/转码视频做内容理解可能涉及平台条款与版权；默认不做。

## 8. 评估方法

1. **离线 fixture**：准备 100–200 条候选（正常/跑题/广告/擦边/重复），人工标注；测安全分类的 precision/recall，安全类误放（false negative）优先于误杀。
2. **影子模式**：先只记录 AI 决策、不实际使用；和人工/随机结果对比，观察 1 周。
3. **小流量**：只对一个测试账户开启 `rank`，对比「跳过/换一条」的手动反馈。
4. **回退率**：AI 超时/非法 JSON/限流的比例；高于阈值自动关闭。
5. **成本**：每次发送的平均 token/费用；设置日/月上限。
6. **回归**：AI 关闭时 `npm test` 全绿，行为与基线一致。

---

## 9. 不建议做的事

- 用 AI 决定「发给谁、发多少、什么时候发」这些会突破风控/社交边界的决策。
- 让 AI 直接调用发送接口；发送必须走确定性流程 + 用户配置。
- 自动回复好友、自动聊天、伪造互动。
- 把 cookies/模板/userid/好友昵称发给外部模型。
- 为了「更智能」下载并分析每条视频（带宽、成本、合规都不划算）。
- 用 LLM 替代「总数 + 时段」的随机分配（这是算法问题，LLM 只会增加不确定性）。
- 在没有人工复核的情况下，让 AI 放行擦边/广告内容。
- 用 AI 绕过验证码/平台风控。

---

## 10. 与三个需求的配合

| 需求 | AI 的关系 |
|---|---|
| 每账户独立配置 + 简化 | 账户级 `aiMode`；自然语言配置草案；AI 不能绕过账户边界 |
| MySQL / PostgreSQL | AI 缓存/决策可存 TEXT；和数据库选型解耦；远程库不影响 AI 调用 |
| 抖音默认推荐 | AI 选片/安全过滤是推荐源可用的关键；AI 不解决 feed 签名，签名仍需 POC |
| 发送全部走 API | AI 只产出候选/评分，不改变发送协议；API 选片的签名问题与 AI 无关 |

---

## 11. 需要拍板

1. **先做哪个**：AI 运维助手（低风险、1–2 天）还是推荐源 AI 选片（价值高、依赖推荐源）？建议先做助手，选片跟推荐源一起上。
2. **模型来源**：云 API（OpenAI-compatible，如 DeepSeek）还是本地模型（Ollama）？敏感账号是否强制本地？
3. **数据边界**：是否允许把视频标题/作者/封面发给外部模型？好友标签是否允许？
4. **视觉审核**：是否接受对 top-K 封面做 OCR/视觉（有额外成本）？
5. **默认值**：AI 默认关闭（推荐）；开启后默认只做安全过滤，还是也做排序？
6. **预算**：每日/每月 token/费用上限；超过后自动关闭 AI 还是仅告警？
7. **人工复核**：不确定内容是否进入待审队列（会阻塞发送）？还是直接跳过？
8. **文案**：是否要花时间做 IM 文本消息协议 POC，以支持 AI 问候语？

## 13. 一句话建议

**先做「AI 运维助手 + 自然语言配置」（不碰发送），再在推荐源开启时做「规则预过滤 + AI 主题/安全评分 + 语义去重」；AI 只做候选筛选和解释，不碰发送动作、收件人范围和风控边界。**


## 3. AI 操作能力（受控）

浮窗 AI 不只是问答，还可以提议账户操作：

- 暂停/继续账户
- 修改每天条数、时段
- 切换视频池搜索 / 默认推荐
- 切换 AI 视频筛选模式
- 替换屏蔽词、启用视频池
- 重排今天未发送时刻
- 刷新纯 API 会话
- 立即发送一条（高风险；确认模式下随批次一次确认，自动模式下直接执行）

流程：**AI 提议 → 服务端白名单校验 → 按用户选择的模式执行 → 写事件**。

- **读操作**：直接回答，不需要确认。
- **确认一次（默认）**：一批写入操作只点一次「确认执行全部」。
- **AI 自动执行**：用户主动选择后，AI 提议的写入操作直接执行。
- 两种模式都只允许白名单操作；AI 不能执行 shell/SQL。
