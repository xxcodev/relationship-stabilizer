# 「慢递」功能计划

> 基线版本：**v0.31.3**（2026-11-26）
> 状态：**M1 已落地（0.32.4）**。名字「慢递」；节奏可配置；点击后由你选时长/节奏/收件人；日常排班让路。
> 一句话：点一下，在接下来 N 小时里，按随机间隔给一位好友慢慢发视频；每条之间不短于「上一条视频时长 + 5 秒」，到点自动收束。

## 0. 先说结论

- **名字：慢递**（Slow Delivery，已确认）。产品叫「心动投递」，慢递是它的反面：不急着投完，像给未来寄一叠明信片。备选见 §1。
- **交互**：首页多一张「慢递」卡。点「开始慢递」先打开选择面板，选时长、节奏、收件人和上限，确认后开始；面板预填上次的选择，所以常用组合只需再点一次确认。
- **算法**：`间隔 = max(随机(下限, 上限), 上条视频时长 + 5 秒)`；首条立即发；下一次落点超过结束时间就收束。
- **与现有排班的关系**：慢递期间日常计划让路，慢递条数独立计算；结束后日常计划继续。慢递期间禁用手动发送。
- **实现**：新增一个纯状态机 + 调度器里一条独立 lane；慢递状态继续放 `account_settings`，不需要新表/新列，SQLite / PostgreSQL 零迁移。互关全量列表会让 MySQL 的 `settings` / `account_settings.value` 从 `TEXT` 扩到 `MEDIUMTEXT`（启动时自动 ALTER，失败忽略），SQLite / PostgreSQL 不受影响。复用现有选片、去重、好友校验、错误处理。

## 2. 一次点击的体验

### 2.1 首页卡片

放在首页 `hero-grid` 下方、统计卡上方，整行一张卡，桌面首屏可见。

**空闲时：**

```
┌──────────────────────────────────────────────────────────────┐
│  慢递 · 细水长流                                      [设置]  │
│  接下来 2 小时，隔几分钟发一条给 小鹿；不占用今日计划。       │
│  间隔 3–10 分钟 · 不短于上条视频 +5 秒 · 上限 60 条           │
│  预计 12–40 条，通常约 18 条                                  │
│                                                              │
│  [ 开始慢递 ]                                                 │
└──────────────────────────────────────────────────────────────┘
```

空闲卡只展示上次/默认设置；点主按钮不直接发送，而是打开下面的选择面板。这样“点一下”之后仍由你决定这次怎么发。

### 2.1.1 点击后的选择面板（已确认交互）

点「开始慢递」不直接发，先弹一个和视频分类选择器同风格的面板；预填上次的选择，常用组合只需要再点一次「开始慢递」。

```
│  这次想陪多久、多久发一条、发给谁？                           │
│                                                              │
│  时长      (30 分) (1 小时) [2 小时] (4 小时) [自定义 120]   │
│  节奏      (5–15 分) [3–10 分] (1–3 分) [自定义 3–10 分]     │
│  收件人    [ 小鹿 ▾ ]   纯 API 可用                           │
│  上限      [ 60 ] 条                                          │
│                                                              │
│  预计 12–40 条，通常约 18 条；不短于上条视频 +5 秒            │
│  [ 取消 ]                              [ 开始慢递 ]           │
└──────────────────────────────────────────────────────────────┘
```

面板里的「开始慢递」才是真正提交；提交后关闭面板，卡片进入「准备中…」。

**进行中：**

```
┌──────────────────────────────────────────────────────────────┐
│  慢递中 · 还剩 01:38:24                            [提前收束]  │
│  已发 7 / 上限 60 · 下一条 18:04（约 3 分钟后）               │
│  发给 小鹿 · 上一条 00:42《……》                               │
│  今日慢递 7 条 · 已让路 2 个日常计划点                        │
└──────────────────────────────────────────────────────────────┘
```

**暂停 / 结束 / 卡住：**

- 暂停：`慢递已暂停 · 倒计时冻结在 01:38:24`，提示点顶部「继续」。
- 正常结束：`慢递已收束 · 共发 18 条 · 19:42 结束`，给「再来一次」和「查看记录」。
- 卡住：`慢递停住了：需要人机验证`（或会话失效 / 好友被停用 / 候选发完），保留已发条数，给处理建议。

### 2.2 一键启动的完整流程

1. 点「开始慢递」——打开选择面板，预填上次的时长/节奏/收件人/上限。
2. 在面板里改成本次想要的值，右侧实时显示预计条数；选好收件人后点面板里的「开始慢递」。
3. 面板写一条 `pending` 状态到数据库，立刻返回；按钮变成「准备中…」。
4. 该账户的调度子进程在 **≤3 秒**内看到请求（包括日计划已经完成、调度器正在 60 秒空闲等待的时候），把状态改成 `running`，并发第 1 条。如果它正好在发上一条或等重试，会等当前动作结束，通常不超过几十秒。
5. 第 1 条成功后，按 §3.1 的公式算下一条；等待、发送、回写，循环。
6. 到结束时间（或达到条数上限）自动收束；如果下一次落点已经超出窗口，就提前收束，不空等。
7. 点「提前收束」：当前这条发完就停，不再开新的。
8. 全程可以在首页看倒计时、已发条数、下一条时间、上一条视频时长。

### 2.3 设置项与默认值

每次点「开始慢递」都会打开选择面板；卡片右上角「设置」也打开同一个面板。默认值用于第一次，成功开始后自动记住这次的选择，下次预填。

| 设置 | 默认 | 范围 | 说明 |
|---|---|---|---|
| 时长 | **2 小时** | 15 分钟–8 小时 | 常用 30 分钟 / 1 / 2 / 4 小时 |
| 节奏 | **3–10 分钟** | 10 秒–60 分钟 | 见 §2.4；下限不能大于上限 |
| 视频时长让路 | **+5 秒** | 0–60 秒 | 你要求的固定 5 秒；留成可调，默认不动 |
| 未知时长兜底 | **30 秒** | 0–300 秒 | 拿不到视频时长时，用 30 秒当“上一条时长” |
| 条数上限 | **60 条** | 1–200 | 安全阀；2 小时 3–10 分钟的常态约 18 条，60 条基本碰不到 |
| 收件人 | 上次选的 / 第一位启用好友 | 账户好友 | 单选；来自账户好友列表（不是互关缓存），慢递期间固定发给这一位 |
| 记住上次选择 | 开 | — | 下次打开面板时预填；每次仍由你确认 |

### 2.4 节奏怎么选（这是最需要你确认的一点）

节奏是可配置的；默认 3–10 分钟只是第一次的初始值，每次开始前都可以在面板里改。你只说了“间隔随机、不低于上条视频时长 + 5 秒”，没有给随机区间的上限，上限决定了两小时到底发几条，差别非常大：

| 节奏（随机区间） | 2 小时大约 | 1 小时大约 | 风险 | 适合 |
|---|---|---|---|---|
| 5–15 分钟 | 8–24 条（约 12） | 4–12 条 | 低 | 很克制，像偶尔想起 |
| **3–10 分钟（推荐）** | **12–40 条（约 18）** | 6–20 条 | 低–中 | 有存在感，又不刷屏 |
| 1–3 分钟 | 40–120 条（约 60） | 20–60 条 | 中–高 | 只适合短时间、短会话 |
| 10–50 秒（现有连发节奏） | 144–720 条 | 72–360 条 | 很高 | 不建议长开，几乎必然触发风控 |

> 上表按“忽略视频时长下限”粗估；实际条数会因视频较长、发送失败、上限截断而减少。
> 现有的 10–50 秒是给“一个触发点连发 6 条”设计的，直接拿来跑 2 小时会变成机器行为——所以我建议慢递单独用分钟级节奏。
>
> 另一种理解是：**以「视频时长 + 5 秒」为基准，再随机加 0–N 分钟**，这样间隔会随视频变长，短片的节奏会更密。默认方案是“先随机、再用视频时长兜底”（§3.1）；如果你要的是前者，告诉我，只改 `gap` 一个纯函数。

## 3. 行为规则

### 3.1 间隔算法

```text
base  = 在 [下限, 上限] 里均匀随机          // 默认 180–600 秒
floor = 上一条视频时长 + 5 秒                // 拿不到时长就用 30 秒 + 5 秒
gap   = max(base, floor)
nextAt = max(上一条开始时间 + gap, 上一条发完 + 1 秒)
```

- **首条立即发**，不随机等待（点击的即时反馈）。
- 间隔按“上一条开始发送”到“下一条开始发送”计算，和现有连发的口径一致。
- 如果一条视频 12 分钟、随机只抽到 5 分钟，则下一条在 **12 分 05 秒**后；如果抽到 8 分钟、视频只有 40 秒，则按 8 分钟走，floor 不生效。
- **不补发**：电脑睡眠、服务重启、手动暂停之后，不会把错过的几条一次性补出来；迟到超过 2 分钟就重新抽一个间隔。
- **结束边界**：下一条的开始时间 `>= endsAt` 时不再发，直接收束；已经开始的那条允许发完。
- 例：17:42 开始，第 1 条视频 40 秒；随机抽到 4 分 12 秒 → 下一条 17:46:12；到 19:42 停止。

### 3.2 生命周期

| 状态 | 含义 | 谁写入 | 首页表现 |
|---|---|---|---|
| `pending` | 面板已下单，调度器还没接手 | 面板 | 「准备中…」 |
| `running` | 调度器正在跑 | 调度器 | 倒计时 + 进度 |
| `paused` | 账户被暂停；倒计时冻结 | 调度器 | 「已暂停，点继续」 |
| `done` | 正常收束（到点 / 到上限 / 窗口排不下） | 调度器 | 「已收束」+ 小结 |
| `stopped` | 用户提前收束 | 调度器 | 「已提前结束」 |
| `blocked` | 人机验证、会话失效、好友不可用 | 调度器 | 「停住了」+ 原因 |
| `exhausted` | 连续两轮找不到没发过的新视频 | 调度器 | 「候选发完了」+ 建议 |
| `expired` | 服务关着/睡过头，醒来已过结束时间 | 调度器 | 「已过期」 |

终态（done / stopped / blocked / exhausted / expired）不会再自动复活；要再跑就重新点一次。

### 3.3 和日常排班、手动发送的关系

- **慢递优先**：慢递一开始，今天的日常计划进入“让路”状态。
  - 会落在慢递窗口内的待触发点，标记为 `skipped`，原因 `slow-mail`；首页时间线显示「让路」而不是「失败」。
  - 窗口结束之后的触发点不受影响，照常按原计划跑。
  - 已经在发送中的那一条日常发送，允许发完，再由慢递接手。
- **条数独立**：慢递不占今日计划的条数，也不改 `burstState` 的 sent / total；首页「今日进度」仍是日常计划的进度，慢递在自己的卡片里计数。
- **手动发送禁用**：慢递 live 期间，顶部「立即发送一次」置灰；`/api/send-now` 服务端返回 409，避免和慢递并发。
- **今日计划重置禁用**：慢递 live 期间，`/api/today/burst-reset` / `/api/today/regenerate` 返回 409，避免把已经让路的触发点重新激活；要重置先收束慢递。
- **自然分享静音**：慢递期间强制关闭「自然分享」的多条连发（它会 1–4 秒发 1–2 条，破坏慢递节奏）。
- **选片/AI/筛选照旧**：慢递走和日常发送完全相同的 `sendOne`，所以去重、屏蔽词、时效、互动门槛、AI 过滤、好友 userid 校验都继续生效。
- **计数口径**：慢递不改今日计划的 `sent / total`；首页「今日进度」仍是日常计划的进度，慢递在自己的卡片里单独计数。记录页和「累计发送」按真实 `sends` 统计，会包含慢递的条数。

### 3.4 失败、暂停、重启

- 单条失败：15 秒后重试 1 次（和日常发送一致）；仍失败就记一轮失败，下一次尝试至少等 `max(下限, 2 分钟)`，不中止整个慢递。如果重算出的下一次已经超出窗口，就按 `done` 收束，保留 `lastError`。
- 连续 3 轮失败：`blocked`，保留错误原因，等人工处理。
- 人机验证 / 纯 API 会话失效 / 好友被停用或删除：立即 `blocked`，不重试。
- 连续 2 轮 `dedup-exhausted`（严格去重后没有新视频）：`exhausted`，提示加视频池、放宽时效或换来源。
- 账户暂停：`paused`，**倒计时冻结**；恢复后 `endsAt` 顺延暂停时长，2 秒后继续。恢复时若已暂停超过 24 小时，直接 `expired`，避免僵尸会话。
- 服务重启 / 电脑睡眠：状态在库里，重启后按 §3.1 的“不补发”规则恢复；已过 `endsAt` 就 `expired`。
- 浏览器模式：慢递期间浏览器由本会话常驻（第一次需要时拉起，结束时关掉），避免每条都冷启动 Chrome；纯 API 模式完全不碰浏览器。

### 3.5 边界

- **跨午夜**：慢递用绝对时间戳，23:30 开始 2 小时会跨到第二天，不受日常计划“按天重置”影响。
- **多账户**：每个账户的调度子进程独立，各自可以跑一条慢递；首页只显示当前查看账户的那条。
- **改配置**：慢递的时长/节奏/上限/收件人在开始时冻结，中途改默认值不影响正在跑的这条；视频来源、池子、筛选、AI 模式仍实时读取。
- **改好友**：收件人固定；如果中途被停用/删除，`blocked`。
- **不跨设备**：面板是 127.0.0.1，慢递只在运行调度器的这台机器上跑；关掉应用就不跑了。

## 4. 技术方案

### 4.1 为什么不复用现有“触发点”

现有触发点是**按天**的：每天重置、按配置条数发、点与点之间用秒级 `burst` 状态。慢递是**临时的一次性会话**：按时间结束而不是按条数、可能跨午夜、还要抢占当天计划。硬塞进 `burstState` 会污染日计划语义，首页进度和“重新开始今天”都会变得难以解释。

所以：**独立状态 + 独立 lane**，只复用发送链路（`sendOne`）和纯函数里的间隔计算（`gapMs`）。

```json
}
```

默认值 key（每账户）：`slowMailDurationMin=120`、`slowMailMinGapSec=180`、`slowMailMaxGapSec=600`、`slowMailMaxSends=60`、`slowMailBufferSec=5`、`slowMailFallbackSec=30`、`slowMailFriend=''`。

### 4.4 HTTP 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/slow` | 默认值 + 当前状态 + 预估 + 好友列表 + 预检（账户启用、调度器锁、API 会话、好友是否可发） |
| POST | `/api/slow/start` | 开始；校验时长/节奏/好友/互斥；写 `pending`，202 返回 |
| POST | `/api/slow/stop` | 提前收束；保留已发条数，写 `stopped` |
| GET | `/api/data` | 增加 `slow` 字段（状态、剩余时间、下一条、预估），首页 15 秒轮询直接渲染 |
| POST | `/api/today/burst-reset`、`/api/today/regenerate` | 慢递 live 时返回 409「先收束慢递」 |
| POST | `/api/send-now` | 慢递 live 时返回 409「慢递进行中」 |

`POST /api/slow/start` 的校验：

- 账户必须是启用状态；否则 409「账户已暂停，先点继续」。
- 该账户的调度器进程必须在运行（`data/run/schedule-<label>.lock` 的 pid 存活）；否则 409「后台调度未运行，慢递不会开始」。首页卡片同时显示警告。
- 同一账户同一时间只能有一条 live 慢递；否则 409。
- 好友必须是当前账户启用的好友；否则 400。
- `durationMin` 15–480；`minGapSec` 10–3600；`maxGapSec >= minGapSec`；`maxSends` 1–200。
- 如果视频来源是「默认推荐」（只能纯 API），要求纯 API 会话可用且好友可发；否则 400，并说明原因。
- 如果当前有手动发送任务在跑，409「手动发送进行中，稍后再开始」。

### 4.5 调度循环

```text
runLoop:
  读账户配置
  如果账户暂停:
    如果 slow 是 running -> 冻结（写 pausedAt），落库
    sleep / continue
  如果 slow 是 live（pending/running/paused）:
    runSlowMail(cfg, slow)
    continue
  r = runSchedule(cfg, day)
  如果 r.slowPending: continue

runSchedule 的每次循环开头:
  如果 slow 变成 live -> 立刻 return { slowPending: true }   // 让路
  把最长等待切片从 30 秒降到 3 秒（只多几次本地读，换来 3 秒内接手）

runLoop 的 60 秒空闲等待（日计划已完成时）:
  也按 3 秒切片检查 slow 状态
  // 否则日计划跑完后点开始，最多要等一分钟才接手

runSlowMail:
  1. 把窗口内会到点的日常计划点标记为 skipped（reason=slow-mail），落库 + 事件
  2. 固定收件人，关闭 naturalShare；每次循环重新读账户配置（保留暂停/改配能力）
  3. 循环：
     - 账户暂停 -> paused；恢复 -> endsAt 顺延
     - 面板写了 stopped/新状态 -> reconcile 后退出
     - now < nextAt -> interruptibleWait(min(2 秒, 剩余))
     - 到点 -> sendOne(cfg, { keepBrowser: true })
     - 失败 -> 15 秒后重试 1 次 -> 仍失败按 §3.4 处理
     - 成功 -> afterSend() 算下一跳、落库、写 slow-send 事件
     - 终态 -> slow-done / slow-blocked / slow-exhausted 事件，退出
  4. 如果这次会话拉起过浏览器 -> stopServer

写回落库前再读一次 slow 状态：如果面板在这期间写了 stopped / 终态，先合并再落库，避免一次发送结果把「提前收束」覆盖回 running。
```

`runSlowMail` 接收可注入的 `now`、`send`、`random`，方便单测不走网络。

### 4.6 UI 细节

- 卡片位置：[首页 hero 区](../src/page.html#L1178-L1210)下方整行；沿用现有玻璃卡片和 `eyebrow` 风格。
- 倒计时：页面用 `endsAt` 本地每秒算，不依赖 15 秒一次的数据刷新；`nextAt` 显示为「约 3 分钟后」。倒计时只改 textContent，不重建卡片 DOM，避免 15 秒刷新时闪一下；离开首页或会话结束后清掉这个 1 秒定时器。
- 设置面板打开时，15 秒刷新只更新状态文字，不重建面板，避免输入到一半被重置。
- **卡住提示**：`running` 但 `nextAt` 已过去超过 2 分钟 → 显示「等待调度器…」；调度器锁不存在 → 显示「后台调度未运行」。
- 设置面板：点「开始慢递」或卡片「设置」打开同一个面板；时长/节奏用 chip，收件人用下拉，上限用 number；面板提交时把本次值写入 7 个 slowMail 配置 key（下次预填），只写这些 key，**不碰** `/api/config` 的全量保存，避免误清空排班。
- 卡片主按钮在空闲态是 primary（打开选择面板）；面板里的「开始慢递」提交；进行中卡片按钮变成「提前收束」（danger/ghost），点击才弹一次确认。
- 顶部「立即发送一次」在 live 时置灰；`setSendButtonsDisabled` 已有，扩展一个条件即可。
- 时间线「让路」：`scheduleRuntime` 把 `status=skipped && lastError=slow-mail` 映射成 `deferred`，chip 文案「让路」，不加 ✗，避免看着像失败；需要把每个点的 `lastError` 一并带进 `scheduleRuntime` 的返回。
- 移动端：卡片在 `.hero-grid` 之后单列，按钮占满宽度。
- 事件文案：`slow-start` / `slow-send` / `slow-retry` / `slow-preempt` / `slow-done` / `slow-stop` / `slow-paused` / `slow-resumed` / `slow-blocked` / `slow-exhausted` / `slow-expired` 都补 `DIAG_TITLES` 和中文摘要；`diagCategory` 的配置类正则加上 `slow`。
