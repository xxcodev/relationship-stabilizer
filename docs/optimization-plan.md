# 心动投递优化计划（暂存）

> 基线版本：**v0.23.0**（2026-11-25）
> 状态：待评审 / 后续执行
> 用途：把此前审计出的优化点整理成可逐项执行的清单；实施时每完成一项勾选，并在 CHANGELOG 记录。

## 0. 背景与约束

当前应用已经具备：多账户、纯 API + 浏览器双通道、互关好友缓存、好友轮换、视频去重和最近 7 天时效过滤。
后续优化应保持这些原则：

- **本地优先**：面板只绑定 `127.0.0.1`；不引入不必要的云端依赖。
- **不破坏降级链**：纯 API 失败仍能回退浏览器，浏览器失败不能静默装作成功。
- **不扩大发送范围**：不能自动把互关好友全部启用并发送；涉及收件人的改动必须显式确认。
- **控制请求频率**：抖音搜索/风控是主要外部风险，优先复用缓存和已有浏览器窗口。
- **先修正确性，再加功能**：暂停、历史、幂等等问题会直接损害信任，排在功能前面。

## 2. P0：正确性与信任问题

### P0-1 暂停立即生效

**问题**
`runDay` 使用启动时的 `cfg` 快照，逐个时段 sleep 后直接发送；中途点「暂停」只修改数据库，不会打断当天剩余时段。面板显示“已暂停”但可能继续发。

**相关代码**
- `src/scheduler.js` 的 `runDay()`：循环 pending 时段，发送前没有重新读取账户启用状态。
- `src/dashboard.js` 的 `/api/control`：暂停只更新 `accounts.enabled`，不重启调度。

**改造建议**
- 在每个时段发送前重新读取账户与配置：`enabled`、好友、时段、视频时效等。
- 把长 `sleep` 换成可中断等待：每 1-5 秒检查一次数据库暂停标记/配置版本。
- 暂停时立即结束 `runDay`，返回 `{paused:true}`，不要标记为失败。
- 恢复时由 `runLoop` 在 5 分钟内重新读取并继续。

**验收标准**
- 任意时刻点暂停，5 秒内不再产生新的发送。
- 暂停不会把未发时段标记成 failed；恢复后能继续。
- 停止/退出应用仍保持原有的 host 清理行为。

**测试**
- 单测：暂停标记存在时 `runDay` 不调用 `sendOne`。
- 集成：用临时 DB 生成未来 1-2 分钟的时段，启动 `runDay`，中途写暂停，验证停止。

### P0-2 完整发送历史与累计数

**问题**
`/api/data` 只取最近 200 条发送，`totalSends = sends.length`；记录页搜索/分页/CSV 都基于这 200 条。超过 200 条后首页“累计发送”会永久停在 200，历史也不完整。

**相关代码**
- `src/dashboard.js` `dataFromDb()`：`listSends({ limit: 200 })`、`totalSends: sends.length`。
- `src/page.html` `loadRecords()` / `renderRecords()` / `exportCsv()`：全部前端过滤。
- `/api/accounts` 用 `listSends({ limit: 100000 })` 计数，历史大时性能差。

**改造建议**
- 新增 `repos.countSends(accountId, filters)`，首页累计数用 `COUNT(*)`。
- 新增 `GET /api/records?account=&page=&pageSize=&q=&bucket=&result=&from=&to=`。
- 新增 `GET /api/records/export.csv`，服务端流式导出全量筛选结果。
- 记录页改为服务端分页；保留当前客户端筛选作为过渡。
- `/api/accounts` 的发送数改用 `COUNT(*)`，不再拉 100k 行。

**验收标准**
- 累计发送 > 500 时数字正确。
- 搜索/筛选能覆盖全量历史，CSV 行数与筛选结果一致。
- 首页 15 秒刷新不随历史增长明显变慢。

### P0-3 发送幂等，失败重试不重复

**问题**
发送失败后 90 秒重试；如果第一次实际已送达、只是响应丢失，没有唯一键，会重复发。当前 `sends` 只有业务记录，没有“发送中/幂等键”。

**相关代码**
- `src/scheduler.js` `runDay()` 的重试分支。
- `repos.insertSend()`：发送完成后才写记录。
- `api-sender.sendVideo()` / `browser-server /send`：结果依赖网络响应。

**改造建议**
- 发送前生成幂等键：`accountId + day + slot + friend + videoId`（或 `clientMessageId`）。
- 新增 `send_attempts` 表或在 `sends` 增加 `send_key` 唯一索引、`status` 字段。
- 流程改为：`insert pending` → 发送 → `update success/failed`；重试前查同一 key 是否已成功。
- 进程崩溃后 pending 超时可按策略置失败或人工确认，避免永久阻塞。
- 浏览器 `/send` 返回结果也写入相同 key。

**验收标准**
- 模拟“发送成功但响应超时”：重试不再发第二次。
- 正常发送仍只产生一条成功记录。
- 迁移不破坏旧 `sends` 数据；旧记录 `send_key` 允许为空。

## 3. P1：稳定性与数据可信

### P1-1 每账户独立配置

**问题**
时段、好友、启用状态按账户隔离；但间隔、每日条数、屏蔽词、视频池、发送模式、自动刷新等是全局 `settings`。切账户后配置不跟着切，多账户会互相影响。

**相关代码**
- `src/dashboard.js` `configFromDb()` / `persist()`。
- `schema/001_init.sql` 的 `settings` 注释也写明“不按账户”。

**改造建议**
- 新建 `account_settings(account_id, key, value)`，或把 settings 改为带 `account_id` 的复合键。
- 迁移旧全局值到每个现有账户，保留默认值行为。
- `/api/config`、`/api/apply`、调度 `runtimeConfig` 都按账户读取。
- 视频池启用状态可继续全局，也可按账户；优先做发送计划参数。

**验收标准**
- 账户 A/B 分别保存不同间隔、条数、屏蔽词，互不影响。
- 切换账户后配置页显示对应账户的值。

### P1-2 浏览器生命周期：窗口内常驻

**问题**
`runDay` 每发一条就 `stopServer`，浏览器模式下一天可能启动/关闭 Chrome 十几次；启动慢、容易被风控，还会关闭用户正在看的实时画面。

**相关代码**
- `src/scheduler.js` `runDay()`：每次发送后 `stopServer`。
- `src/scheduler.js` `startServer()` / `stopServer()`。
- 用户实时画面也依赖同一个 browser-server 端口。

**改造建议**
- 区分“调度占用”和“用户查看”引用计数，不能因调度结束就关掉用户正在看的窗口。
- 一个发送窗口内保持浏览器常驻；空闲超过 N 分钟或窗口结束再关。
- 纯 API 成功时不要启动浏览器；API 失败再按需启动。
- 增加浏览器启动超时/端口占用检查。

**验收标准**
- 一个窗口内只启动一次浏览器（无 API 回退时）。
- 用户打开实时画面后，调度发送不会关闭该窗口。
- 发送结束后的空闲回收有明确日志。

### P1-3 错误分类与失败通知

**问题**
`picker.pick` 的 `catch` 会静默跳过池子，502、访问过多、验证码、页面结构变化最后都变成 `no candidate`；用户无法判断是网络、风控还是配置问题。调度失败也没有系统通知。

**相关代码**
- `src/picker.js` `pick()` 的 try/catch。
- `app/main.js` 的 `notify()` 目前主要用于 API 会话刷新。

**改造建议**
- 定义错误类型/结果码：`captcha`、`blocked`、`network`、`page-changed`、`no-candidate`。
- 浏览器 `/state` 标题/正文检测验证码中间页、502、访问过多并回传。
- 事件日志写明确原因；面板首页显示最近一次失败原因。
- 发送失败、连续失败、验证码、会话过期触发系统通知；可选 Webhook/Bark/Telegram。
- 对连续失败加冷却，避免 5 分钟一次刷事件。

**验收标准**
- 人为制造 502/验证码时，面板和日志能区分原因。
- 失败通知能到达；同一天同一原因不刷屏。

### P1-4 自动备份、日志轮转、数据保留

**问题**
`src/backup.js` 只有手动执行；`sends`/`events` 无限增长；日志 `dashboard.log`、`schedule*.log`、`app.log` 没有轮转，长期运行会占空间。

**相关代码**
- `src/backup.js`（手动 CLI）。
- `src/host.js` 日志按追加写，无大小控制。
- `schema/001_init.sql` 只有少量索引。

**改造建议**
- host 每天自动备份一次（`VACUUM INTO`），保留 7 天/4 周；备份目录可配置。
- 日志按大小/日期轮转（如 10MB × 5 份），保留最近 N 份。
- `events` 保留 90 天；`sends` 可保留全部，但面板只查分页；如空间敏感可归档到月度表/JSON。
- 增加索引：`sends(account_id, day, ok)`、`events(event, ts)`，先跑 `EXPLAIN` 验证。
- 面板提供“立即备份/下载备份/恢复”入口（恢复需二次确认）。

**验收标准**
- 连续运行 7 天日志/备份数量受控。
- 备份可恢复到临时目录并通过 `verify`。
- 大历史查询不出现明显全表扫描。

### P1-5 CI 全量测试 + lint

**问题**
CI 只跑 5 个旧测试文件，新增的 `friend-picker`、`video-picker`、`pools`、`api-sender` 测试没有在 CI 执行；没有 lint/format/typecheck。

**相关代码**
- `.github/workflows/ci.yml` 的 `node --test ...` 文件列表。
- 本地 `npm test` 现在是全量 60 项。

**改造建议**
- CI 改为 `npm test`，或列出全部纯函数测试；浏览器测试单独安装 Chromium 后运行。
- 加 ESLint（至少 `no-undef`、`no-unused-vars`、`no-floating-promises` 可按需）和 Prettier check。
- 加 `node --check` 覆盖所有 `src/*.js`、`app/*.js`。
- 可选：用小规模临时 DB + ephemeral dashboard 做集成测试。

**验收标准**
- `npm test` 在 CI 全绿。
- PR 能发现未定义函数/语法错误/格式问题。
- 新加测试文件不会再被 CI 遗漏。

### P1-6 严格好友日限/冷却

**问题**
当前好友轮换只在“当天成功次数最少”的好友中选；所有好友都发过一轮后仍会进入下一轮。若启用好友数少于每日条数，仍会重复发给同一个人。

**改造建议**
- 增加设置 `friendDailyMax`（默认 1）和/或 `friendCooldownHours`。
- 达到上限后跳过该好友；全部好友都达到上限时，跳过剩余时段或按配置停止并记录原因，不要静默重复。
- 首页/记录页显示每位好友今日已发数；超出时给出提示。

**验收标准**
- 1 位好友 + 每日 10 条时，严格模式只发 1 条并明确记录“好友已达上限”。
- 关闭严格模式时保持现有公平轮换行为。

## 4. P2：产品与体验

### P2-1 发送前视频预览与「换一条」

- 在快速发送和定时发送前展示候选：封面、标题、作者、点赞、发布时间、链接、所属池。
- 提供「换一条」「跳过这个池」「预览下一条」。
- 复用 `apiSender.pick` 的候选结构，新增只选片接口返回更多字段/候选列表。
- 注意：预览只读，不要因为预览产生发送记录。

### P2-2 统一互关好友与账户好友来源

- 快速发送用互关缓存；定时排班用 `friends` 表。用户看到两套名单，容易误解。
- 方案 A：快速发送下拉增加「互关 / 账户好友」来源切换。
- 方案 B：把互关好友显式同步到账户好友（默认只同步选中项），排班统一用账户好友。
- 方案 C：排班也支持“互关好友作为候选”，但必须显式开启，且发送前告知范围。
- 不建议默认自动把所有互关加进发送列表。

### P2-3 调度日历、节假日、按好友时段

- 月/周日历显示已发、待发、失败、跳过。
- 支持节假日/临时停发日；支持单日调整总量。
- 支持按好友设置可发送时段、每周上限；与 P1-6 一起设计。
- 需要新表或 JSON 配置；注意时区和夏令时。

### P2-4 多账户健康总览

- 一屏显示每个账户：启用状态、今日进度、下次发送、会话剩余时间、浏览器状态、最近错误。
- 支持批量暂停/继续/刷新会话，但每项操作要有确认和结果反馈。
- 把 `/api/accounts` 的 N 次 100k 查询替换为聚合计数。

### P2-5 签名、公证与自动更新

- 当前 macOS 构建未签名/未公证；Windows 包未验证。用户需要手动替换 app。
- 加 Developer ID 签名 + notarization；Windows 代码签名。
- 接入 `electron-updater`，提供“检查更新/下载/重启安装”，保留手动安装路径。
- 发布前做一次干净机器安装测试。

### P2-6 面板访问令牌（暴露时使用）

- 如果以后通过 Tailscale、反向代理或局域网访问面板，`127.0.0.1` 绑定不再足够。
- 增加可选 token（Header 或 HttpOnly Cookie），所有 `/api/*` 写操作校验；GET 只读也建议校验。
- 保持默认关闭，避免本地使用变复杂；开启时生成随机 token 并写入用户数据目录。
- 增加 CSRF 防护（SameSite Cookie / 自定义 Header）。

## 5. P3：工程与长期维护

### P3-1 前端拆分与可访问性

- `src/page.html` 已 2000+ 行，内联 CSS/JS；按 view/组件拆分，或引入最小构建步骤。
- 下拉/弹层补焦点陷阱、`aria-live` 状态提示、键盘操作说明。
- 表格在小屏下的横向滚动/卡片化；检查颜色对比度。
- 增加“减少动效”适配（已有 `prefers-reduced-motion`，继续覆盖新组件）。

### P3-2 DB 索引、归档与报表

- 为高频查询补索引并用 `EXPLAIN QUERY PLAN` 验证：
  - `sends(account_id, day, ok)`
  - `sends(account_id, ts)`
  - `events(event, ts)`
- 发送历史可按月归档；面板提供“按周/月报表”：发送量、成功率、好友分布、池分布。
- 报表计算尽量走 SQL 聚合，不要拉全量到前端。

- 默认推荐视频源（0.25.0，纯 HTTP）：捕获首页 feed URL 重放；`sends.source` 记录来源。
- AI 旁路（0.25.0）：只读运维助手、自然语言配置草案、推荐源安全过滤/排序；默认关闭。
- 可选 MySQL/PostgreSQL（0.25.0）：默认 SQLite，面板配置连接，重启生效。
- 移动端 `.main` 横向溢出修复。
- 全局贝母氛围 + 账户页简化重排（0.24.0）。
- 头部玻璃条、卡片与背景贝母色贯通、移动端两行导航（0.24.1）。
- 去掉卡片填充/滚动色块，贝母色直接穿过卡片（0.24.2）。

以下建议明确**不采用**：

- 随机翻到搜索结果深页：实测会跑题（如“韩剧”第 2 页出现动漫）。
- 随机热榜/随机热词：内容不可控，跑题概率高。
- 自动把所有互关好友加入发送范围：涉及收件人，必须人工确认。
